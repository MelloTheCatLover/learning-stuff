# Dynamic Programming (пока введение)

Идея — решаю маленькие подзадачи, запоминаю ответы, и из них собираю большую. Как индукция в математике: база это база, переход это шаг индукции. Только тут не доказываю, а считаю.

Залез сюда раньше времени ради одной Hard задачи (3041), по плану это 22-я тема.

## Когда DP

- одни и те же подзадачи считаются много раз
- ответ собирается из ответов подзадач
- в условии: «сколько способов», «минимальная/максимальная стоимость», «можно ли», «самая длинная»
- и на каждом шаге есть **выбор**

## Рецепт — 4 вопроса до кода

1. **Что храню** — что значит `dp[i]`, словами
2. **Переход** — как `dp[i]` получить из предыдущих
3. **База** — самые маленькие случаи
4. **Ответ** — где он (`dp[n]`, максимум по всем и т.д.)

## Фибоначчи на примере

Обычная рекурсия — O(2ⁿ), потому что `fib(3)` считается много раз.

С мемоизацией (сверху вниз):
```ts
function fib(n: number, memo = new Map<number, number>()): number {
    if (n <= 1) return n;                  // база n <= 1, а не n < 1!
    if (memo.has(n)) return memo.get(n)!;
    const res = fib(n - 1, memo) + fib(n - 2, memo);
    memo.set(n, res);
    return res;
}
```

Таблицей (снизу вверх) — цикл, и раз нужны только два прошлых, хватит двух переменных → память O(1).

Важно: мемоизация уменьшает **количество вызовов** (2ⁿ → n), но **не глубину стека** — она все равно n. Я сначала думал наоборот.

| | мемоизация | таблица |
|---|---|---|
| как | рекурсия + кэш | цикл |
| плюс | легко написать из рекурсии | нет стека, можно ужать память |
| минус | стек O(n), в JS может переполниться | надо продумать порядок |

## DP vs жадный

Жадный берет лучшее прямо сейчас и не передумывает. Монеты [1, 3, 4], сумма 6: жадно 4 + 1 + 1 = 3 монеты, а можно 3 + 3 = 2. DP проверяет все варианты.

(У меня в 2567 первая версия была как раз жадной эвристикой — и ломалась.)

## Переходы, которые надо знать

- **70 Climbing Stairs** — `dp[i] = dp[i-1] + dp[i-2]`, это тот же Фибоначчи
- **746 Min Cost** — `dp[i] = cost[i] + min(dp[i-1], dp[i-2])`
- **198 House Robber** — `dp[i] = max(dp[i-1], dp[i-2] + a[i])` — пропустить или взять
- **322 Coin Change** — `dp[x] = 1 + min(dp[x - c])`, `dp[0] = 0`

## 3041 — DP по значению

Самое интересное. Каждое число можно оставить или +1, найти самую длинную цепочку подряд.

- `dp[v]` — длина самой длинной цепочки, которая **заканчивается на числе v** (индекс — само число, а не позиция!)
- сортирую, чтобы к моменту x все меньшие уже посчитаны
- для каждого x два варианта:
  ```
  dp[x + 1] = dp[x] + 1     // сначала это! пока dp[x] старое
  dp[x]     = dp[x - 1] + 1
  ```
- нет в таблице → 0
- ответ — максимум по всем, включая `dp[x + 1]`

Порядок важен: если сначала обновить `dp[x]`, то одно число займет две клетки. Надежнее посчитать оба значения в переменные и потом записать.

Если значения до 10⁶ — массив, быстрее. До 10⁹ — Map.

## Что вынес

- DP по значению, когда ответ — цепочка значений
- сколько вариантов у элемента — столько формул перехода
- при обновлении на месте не читать уже обновленное (так же в рюкзаке перебирают с конца)
- сортировка = порядок вычисления
- проверять решение перебором на маленьких входах

## Где я ошибался

- база `n < 1`
- думал мемоизация уменьшает стек
- в 3041 думал, что `dp[v]` — это число, а это длина
- `dp[x + 1] = dp[x - 2] + 1` — цепочка растет на 1, под x+1 стоит x
- база `dp[0] = 1`, а там 0
- `dp.get` вместо своего `get` → `undefined + 1 = NaN`
- максимум брал только по `dp[x]`, а цепочка часто кончается на `x + 1`
